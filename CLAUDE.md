# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

rustydocs is a Go CLI that finds **stale documentation** by analyzing git history. It walks a content tree, runs `git blame` per file, groups lines into sections (by Markdown headers) and reports the sections whose most-recent change is older than a threshold — with optional propagation from reusable includes (Hugo shortcodes and Mintlify snippets today). Output is Markdown, HTML, and JSON. Built for docs maintainers and CI.

## Commands

```bash
go build -o rustydocs ./cmd/rustydocs              # build
go test ./...                                       # tests
go test -cover ./...                                # tests with coverage (≥80% per pkg)
go test -race ./...                                 # race detector
go vet ./...                                        # vet
gofmt -l .                                          # formatting check (must be empty)
make build                                          # build with version ldflags

# run
./rustydocs --content-dir ./docs --output-dir ./reports --threshold-days 90
./rustydocs --config config.json
go install github.com/nrynss/rustydocs/cmd/rustydocs@latest
```

CI (`.github/workflows/ci.yml`) runs `go build`, `go test`, and `go vet` on Linux, Windows, and macOS, plus a `gofmt` check. The release workflow (`.github/workflows/release.yml`) fires on a `v*` tag and cross-builds linux/darwin/windows × amd64/arm64 with SHA256 checksums. All actions are pinned to commit SHAs.

## Architecture

Pipeline in `cmd/rustydocs/main.go`: flags → `config` → `analyzer.AnalyzeWithProgress` → `report.Generate{Markdown,HTML,JSON}`.

- `internal/config` — JSON config + CLI defaults, `Validate`, staleness tiers, and the **profile registry** (`profile.go`): a `Profile` bundles content extensions, root markers, reusable patterns and a `Resolver` (`none` / `hugo` / `path`) that the analyzer hands to `parser.NewReusablePatternsFor`, so resolution is driven by the resolved profile rather than inferred from which roots happen to be set; built-ins are `markdown` (default, no reusable detection), `mintlify` (`.md`/`.mdx`, markers `docs.json` or legacy `mint.json` — each carrying a *content predicate* (`markerPredicates`/`isMintlifyConfig`: the file must parse as a JSON object with a Mintlify-ish key or `$schema`), so an unrelated `docs.json` never selects it — `<Snippet file="…" />` in either quote style **plus `MDXComponentPattern` for imported components** (`ImportMap: true`, #68), resolved with the path resolver — bases by capture shape: `/…` → root; `./…`/`../…` → the page's dir first; a **bare** name (the form real Mintlify repos overwhelmingly use) → `<root>/snippets/`, `<root>/_snippets/`, root, then the page's dir last (`directPathBases`), #7 — registered *after* `hugo` so a Hugo site carrying a `docs.json` keeps shortcode tracing on a same-directory tie, while the nearest-marker walk already handles nesting) and `hugo` (markers: a `layouts/` or `themes/` directory, a `hugo.{toml,yaml,json}` file, or a `config/_default/` Hugo config (`hugo.*`/`config.*` under it) — the config-file and `themes/` markers matter because git does not track an empty `layouts/`; a marker may be a relative path, and the trailing-`/` directory rule applies to its last segment). `ApplyProfile` resolves `--profile`/`"profile"` or auto-detects with a nearest-marker walk up from the content dir — **marker-driven only**: the project root lives in one field, `Config.ProjectRoot` (`json:"project_root"`, `--project-root`), and supplying it never biases profile selection (it used to force `hugo`, which broke every other profile that needs a root). The Hugo-era `"hugo_root"` survives as a deprecated JSON alias: `Config.UnmarshalJSON` decodes it into the unexported `legacyHugoRoot`, `foldLegacyRoot` folds it into `ProjectRoot` (idempotently, guarded on `ResolvedProfile.Name == ""`) and records `rootSource`; `project_root` wins when both are set, the legacy key adds a deprecation warning to `Config.Warnings`, and it alone keeps the legacy compat path of selecting `hugo` when marker detection found nothing (`detectNearest`: the first level holding any profile's marker wins, registry order only breaks ties at the same level; `Profile.DetectRoot(contentDir, warn)` is the single-profile, predicate-aware form of the same walk that ApplyProfile uses — the only exported entry point, deliberately: the old marker-list `DetectRoot` skipped the predicates and was removed as a trap; `walkUp` stops at the nearest enclosing git repo root — the level holding `.git` is searched, nothing above it — so a checkout under an unrelated `themes/`/`layouts/` dir is not misdetected; the bound is a `.git` directory or a `.git` file pointing at a linked worktree, while a `.git` file pointing into a parent's `.git/modules/` marks a **submodule** and is walked *through* (`gitFileIsSubmodule`), so a Hugo site whose `content/` is a submodule still resolves against the parent's `layouts/`/`hugo.toml`; an unreadable or unparsable `.git` file stops the walk, and only a tree with no `.git` above it walks to the filesystem root) and fills only the settings the user left empty (the legacy reusables-dir flow additionally restores the hugo *extensions*, not just the patterns, so `.mdx` keeps being analyzed) — call it after merging file + CLI config and before `Normalize`; the analyzer calls it itself if `ResolvedProfile` is unset. A project root the *user* supplied (`--project-root`/`project_root`/legacy `hugo_root`, recorded as `RootFromUser` the way `ExtensionsFromUser` is) must exist and be a directory or `ApplyProfile` errors naming the flag or key (`validateExplicitRoot`, `os.Stat` so a symlink to a real dir passes); a detected root always exists so detection is unaffected. Marker predicates now return `(bool, error)`: "not a match" is silent, but a candidate that could not be *read* is appended to `Config.Warnings` — worded about the *marker* being skipped, not about the profile being rejected, since another marker in the same directory may still select it — (`json:"-"`, reset per call) via the walk's `markerWarnFunc` and printed by main.go after the banner — the config package never prints. `isMintlifyConfig` reads through an `io.LimitReader` capped at `maxMintlifyConfigBytes` (1 MiB), which is what actually bounds memory since each top-level value is buffered whole before its key is judged. `Normalize` reconciles the reporting threshold with the staleness tiers (clamps `warning` ≤ `threshold_days`) so a stale section can't be classed `fresh`.
- `internal/analyzer` — `filepath.WalkDir` over the content dir filtered by the `content_extensions` allowlist **and the default exclusions** (#69): the dir callback prunes (`filepath.SkipDir`) any directory whose base name `config.IsDefaultExcludedDir` rejects (a dot-directory, or one of `config.DefaultExcludeDirNames` — `build`/`dist`/`node_modules`/`vendor`) or that is a nested *standalone* repository (`isDefaultExcludedDir` → `config.IsRepoRoot`, the same predicate `config.walkUp` uses: a nested clone or linked worktree is a different project that `GetGitRootForPath` would resolve against, while a **submodule** belongs to the repo under analysis and is walked *through*/into by both walks — pruning it silently dropped real docs, #69 review); the content root is never pruned (it is usually the repo root, and may legitimately be a dot-dir). After the walk, `filterGitIgnored` drops the files git ignores in one `git.CheckIgnore` (`git check-ignore --stdin -z`, index consulted so a *tracked* file is never dropped; an error — e.g. not a repo — means no filtering, and those files stay *unknown* as before). All of it is off under `Config.NoDefaultExcludes` (`--no-default-excludes` / `"no_default_excludes"`); `exclude_dirs`/`exclude_patterns` are additive; `exclude_dirs` now prunes the subtree too (`isUserExcludedDir`, counted by `DirsExcluded` — patterns cannot prune, since `a*` matches the dir `api` but not `api/x.md`), while `exclude_patterns` stays a per-file filter counted by `FilesExcluded`. New diagnostic accessors: `DirsSkipped`/`SkippedDirNames`/`DirsExcluded`/`FilesGitIgnored`, printed by main.go's `describeDefaultExcludes` (before the zero-files warning, not suppressed by it). Then a worker pool (`runtime.NumCPU()`, channel-fed) that analyzes each file, and the staleness math (section vs threshold, oldest/most-recent dates, reusable freshness folding). A file with no git history sets `FileAnalysis.HistoryMissing` (reported as *unknown*, never *fresh*). Reusable refs go through `parser.ResolveReusable`, whose `Resolution` distinguishes resolved / unresolved / **skipped**; a skipped ref (import-map only) is dropped entirely — no report row, no unresolved count (#68). `AnalyzeWithProgress` creates the run's one `git.FileInfoCache` before the pool starts and passes it to every `analyzeFile` (and on to that file's `ReusablePatterns`), so a shared include costs one `git log` per run rather than one per referencing page (#65) — it must be created here, since `ReusablePatterns` is built per file. `nowFunc` is a package var so tests can pin "now".
- `internal/git` — wrappers around `git blame --line-porcelain` (streaming parser) and `git log`; per-directory git-root cache so multiple repos work; plus `FileInfoCache`, a run-scoped memo for `GetFileLastModified` (explicit value, not package state; nil receiver = no caching; caches negative results; per-entry `sync.Once` so concurrent askers share one subprocess; keyed on the absolute symlink-resolved path) — safe because one run analyses one commit state, and deliberately not extended to blame output or across runs (#65).
- `internal/parser` — section/paragraph chunking by header regex, reusable-reference detection (regex), and resolution, dispatched on the resolved profile's `Resolver`: **hugo** (shortcode → `layouts/shortcodes/…`, then each `themes/<theme>/layouts/shortcodes/…` in Hugo's lookup order (project wins; symlinked theme directories are followed), + traced data files); **path** (`ResolverPath`, Mintlify — the capture *is* a file path, resolved in the order `directPathBases` implements: a `/`-prefixed capture against the project root only; a `./`/`../` capture against the referencing page's directory first, then the shared bases; a bare capture against the shared bases — `<root>/snippets/`, then `<root>/_snippets/`, then the root — with the page's own directory last, as a tolerant fallback. `.mdx`/`.md` (and `index.*`) fallback for an extensionless capture, and a containment check that ignores anything escaping the root); or a reusables dir (legacy, resolver-independent). On top of `path` sits the **MDX import map** (`importmap.go`, gated by `Profile.ImportMap`, mintlify only today, #68): `importsFor(sourceFile)` reads the *whole* page once (memoized per source file; imports live above the sections that use them, so a section-scoped scan would never see them), captures `import X from "…"` / `import { A, B as C } from "…"` (default, named, alias, namespace, combined, multi-line) with `importStatementPattern`, and maps each local binding to a path resolved by the same `resolveDirectPath`. Only `.md`/`.mdx` (and extensionless) imports are followed; a `.jsx`/`.js`/`.css` import or a bare package specifier (`isBareModuleSpecifier`) becomes `importTarget{skipped:true}` — freshness folding only makes sections look *fresher*, so a restyled shared component would mark every importing page fresh. `ResolveReusable` consults the map first, falls through to the path/hugo/dir resolution, and only then calls a *component-shaped* capture (`isComponentSymbol`) `ResolutionSkipped` rather than unresolved — which is what lets the mintlify profile carry `config.MDXComponentPattern` (shared with hugo) without every `<Card />` becoming a broken include. `DisplayName` consults the map too (`displayTarget`), so an imported-but-uncommitted snippet still reports its path. Because the path resolver has to know which page a reference came from, `GetReusableInfo(ref, sourceFile, rp)` and `CalculateSectionStaleness(section, sourceFile, rp)` both take the containing file's absolute path; `NewReusablePatterns(patterns, exts, dir, hugoRoot)` remains as the pre-profile shim that infers `hugo`/`none`.
- `internal/report` — Markdown (string builder), HTML (`html/template`, embedded via `go:embed`), JSON. Shares a `nowFunc` var for deterministic day-deltas in tests; unknown dates render consistently (`—` / level `unknown`) across all three formats.
- `internal/testutil` — test-only helper: `NewRepo(t)` builds a temp git repo and `Commit(when, msg, files)` lands commits with controlled author/committer dates, so blame/log timestamps (and staleness) are deterministic. Skips when `git` is absent.

**Zero external dependencies — standard library only. Keep it that way** (goldmark is the one sanctioned exception under consideration, see #27; it's pure-Go). Do not add CGO.

## Gotchas

- **Requires `git` on PATH and full history.** Blame needs an unshallowed clone — CI and any container must use `fetch-depth: 0`. Files with no resolvable history (uncommitted, shallow, or not a repo) are reported as *unknown* with a stderr warning and a `files_missing_history` count — not silently treated as fresh.
- **The walk is pruned before the allowlist even runs** (#69): dot-dirs, `build`/`dist`/`node_modules`/`vendor`, nested standalone repos (**not** submodules), git-ignored files, and the user's `exclude_dirs` are skipped by default. Files under a pruned directory are never visited, so they land in *no* other counter — `DirsSkipped`/`SkippedDirNames`/`DirsExcluded`/`FilesGitIgnored` are the only explanation a user gets, which is why the stderr note prints whenever they are non-zero and why `describeNoFilesMatched` has a branch per cause. `--no-default-excludes` restores the old behaviour for the built-in rules only; it never disables the user's own `exclude_dirs`.
- **Only files matching `content_extensions` are analyzed**, and the default depends on the resolved profile: `markdown` scans `.md`/`.markdown`; `hugo` adds `.mdx`; `mintlify` scans `.md`/`.mdx`. Set `content_extensions` in config or pass `--extensions` to override. A run that matches zero files prints a stderr warning naming the profile and extensions in force; a run that matches *some* files but skips files whose extension is content under another built-in profile (`config.KnownContentExtensions()`, today just `.mdx`) prints a stderr note instead, naming the count, the skipped extensions and the two remedies. Both leave the exit code unchanged, and the note is suppressed when zero files matched so only one message is printed.
- **An import-map profile must keep its skip rules honest** (#68). `ResolutionSkipped` suppresses a reference entirely: no report row, no unresolved count, no stderr note. That is right for `<Card />` and for a `.jsx` import, and catastrophic if the buckets ever blur — a genuinely broken `.mdx` import quietly becoming "skipped" would make the tool silently stop reporting the one failure it can diagnose. The rule is: skipped ⇔ *never was an include* (an unimported tag, a non-content or package import); a content import that names no file is always `ResolutionUnresolved`.
- **Unresolved includes are a stderr note, never a failure.** `describeUnresolvedReusables` (main.go) fires when `Results.UnresolvedReusables() > 0` **and** the resolved profile's `Resolver` is `ResolverPath`, naming the profile, the count and up to `unresolvedRefsShown` of the captures (then "and N more"); it adds a "no project root was found / pass `--project-root`" sentence only when the root is empty. The resolver gate matters: `hugo`'s component pattern captures every capitalised JSX tag, so an ungated note was ~88% noise on MDX Hugo sites (their unresolved rows still show as `unknown` in the reports). A new profile that resolves includes must set `ResolverPath` — or extend this gate — or its broken includes exit 0 with empty stderr. Gating the whole note on a missing root (as it once did) hid the common case: a Mintlify repo whose root is found and whose snippet paths still resolve to nothing.
- **The embedded HTML template is `internal/report/templates/report.html`** — the `go:embed` path is relative to the report package.
- **Section detection is a per-line header regex**, so a `#` line inside a fenced code block can be misread as a heading; replacing it with goldmark is tracked in #27. The **import scanner** has its own fence tracker (`parser.fencedSpans`, ``` and `~~~`, info strings, indented and unclosed fences) and skips imports inside fenced regions — deliberately scoped to imports, because following an example import folds a file's date in and makes a page look *fresher*, and because a decoy import in a fence would otherwise shadow the real one below it (first-import-wins). Do not grow it into a second CommonMark parser; #27 owns the header side.
- **`Resolution` provenance** (#68 review): only a capture the *component* pattern (`config.MDXComponentPattern`) produced may be `ResolutionSkipped`. `FindReusables` records every capture an **include** pattern yielded (`ReusablePatterns.includeCaptures`), and such a capture must resolve or be counted unresolved — `<Snippet file="AlsoMissing" />` is capitalised, extensionless and separator-free, which is exactly the component shape, yet it is an include and the path resolver supports that spelling. A capture with no recorded provenance falls back to the shape heuristic. A new include pattern therefore needs nothing; a new *component-usage* pattern must be `MDXComponentPattern` itself or the gate widens.

## Direction (see GitHub issues / epics)

- **Positioning:** CI-first staleness *triage* (age-based, section-level, format-agnostic), **not** code↔doc *drift* correctness. Lean into the GitHub Action (#29) and packaging (#30).
- **Tool-agnostic profiles** (#10): Hugo and Mintlify (done) + Starlight/MkDocs/Docusaurus/RST/AsciiDoc/… Starlight is first-class (#18). New direct-path formats (VitePress, #15) reuse `ResolverPath`.
- **Agentic drift** (#26): rustydocs does cheap triage; an AI agent verifies real drift on the shortlist (#25). ast-grep stays optional/pluggable (#28).
